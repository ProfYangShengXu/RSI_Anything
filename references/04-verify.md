# 04 执行与验证（G4）

## 三条同

### 同起点（具体怎么做，不是口号）

```
① H0 用 commit/tag 钉住；每臂都从【同一个 commit】起跑
② 改动以 patch 存在，不叠在上一版上：H0+patchA vs H0+patchB
③ 更强的形式：本题内先跑一次参考执行（reference），再跑候选
   这样比的是“同一道题上改前改后”，题目难度被控掉
```

反例：在上一轮改完的代码上继续改，然后跟历史 baseline 比分数 —— 那就是不可归因。

### 同预算

调用次数/墙钟/金额一致；一臂提前结束要截齐，否则比的是“多试几次”。

### 同评测壳

判据/题集/GT/计数器 hash 未变（`freeze_hashes.py --verify`）；变了作废。

## 结论强度按样本量

```
n < 50/臂    只报个案方向，禁 p 值、禁“显著”
n ≥ 100      配对精确检验（McNemar exact）
n ≥ 几百      才谈误差棒与置信区间
```

**先算样本量再决定跑多少题。** 同一批题跑十遍还是 15 个样本。

## 报告必带四项

```
reward
总成本
成本分母（每题 / 每次成功）→ cost per solved task
失败签名（不是“失败了”，是“因为什么失败”）
```

## 迁移三轴（至少验两个）

```
换题     任务级留出，留一批不碰
换模型   同改法换 backbone
换工具面 同任务换接口
```

阈值先写死再跑：

```
留出收益 ≥ 一半  部分迁移；≥ 八成  成立
换模型后归零     model-specific
换工具面仍成立   才可标 invariant
```
