# 04 执行与验证（G4）

## 三条同

### 同起点

```
① H0 用 commit/tag 钉住；每臂都从同一个 commit 起跑
② 改动以 patch 存在，不叠在上一版上：H0+patchA vs H0+patchB
③ 更强的形式：本题内先跑一次参考执行（reference）
   —— 用当前壳跑一遍，拿到它在这道题上的轨迹与产物，作为“改前”对照；
   然后跑候选，比同一道题上两条轨迹的差异（不是比历史分数）
```

反例：在上一轮改完的代码上继续改，再跟历史 baseline 比分数 —— 不可归因。

### 同预算

调用次数 / 墙钟 / 金额一致；一臂提前结束要截齐，否则比的是“多试几次”。

### 同评测壳

判据 / 题集 / GT / 计数器 hash 未变（`freeze_hashes.py --verify`）；变了作废。

## 结论强度按样本量

```
n < 50/臂     只报方向（精确检验可算，但功效不足，不报 p、不写“显著”）
50–99/臂      精确检验可作参考；能检测的最小差异约 15pp
≥ 100/臂      精确检验可作结论；可检测约 8pp
≥ 几百        才谈误差棒与置信区间
```

★ **exact 检验在小样本上也合法**，问题不是合法而是**功效**：样本太小时不一致对数太少，
即使方法真有用也检不出来。门槛不是“能不能算”，是“能不能下结论”。

## 报告必带四项

```
reward
总成本
成本分母（每题 / 每次成功）→ cost per solved task
失败签名（不是“失败了”，是“因为什么失败”）
```

## 迁移三轴（至少验两个）

```
换题     任务级留出，留一批不碰
换模型   同改法换 backbone
换工具面 同任务换接口
```

阈值用**相对保留率**，分母写清楚：

```
Δ_arm = arm 分数 − H0 分数
保留率 = Δ_留出题 / Δ_原题
≥ 0.5 → 部分迁移；≥ 0.8 → 成立；< 0.5 或为负 → 过拟合本批题
```

阈值先写死再跑，跑完不许改。
